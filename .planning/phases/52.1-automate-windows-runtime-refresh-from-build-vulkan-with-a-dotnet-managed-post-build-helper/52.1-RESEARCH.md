# Phase 52.1: Automate Windows runtime refresh from build-vulkan with a dotnet-managed post-build helper - Research

**Researched:** 2026-05-18  
**Domain:** .NET-managed Windows runtime refresh automation for the Avalonia control’s committed mdCAD bundle  
**Confidence:** HIGH

## User Constraints

### Locked / explicit constraints from the phase brief
- Add a **dotnet-managed C# helper**; do not rely on PowerShell for the refresh flow.
- Keep scope limited to Phase 52.1; do **not** broaden into Phase 53 consumer-proof work or Phase 54 docs work.

## Summary

The repo already has the core packaging seam Phase 52.1 should reuse: `samples/avalonia-mdcad-control/MdCad.Avalonia.Control.csproj` includes `runtime\win-x64\**\*` as content, links it into `mdcad-runtime\...`, and copies it with `PreserveNewest`. The control then resolves the runtime only from `AppContext.BaseDirectory\mdcad-runtime\mdCAD.exe` through `MdCadRuntimeResolver`. That means the right place to hook automation is the control project itself, not the hosts and not the control runtime resolver.

The existing maintainer workflow is still PowerShell-only: `scripts/refresh-pinned-mdcad-runtime.ps1` clears the committed runtime folder and recopies files from `build-vulkan\bin\Release`. Phase 52.1 should replace that with a small C# console helper that shells out directly to `cmake` using `ProcessStartInfo.ArgumentList`, builds only the `mdCAD` target in the already-configured `build-vulkan` directory, then refreshes the committed `runtime\win-x64\mdCAD.exe`. The csproj target should be **opt-in by property**, Windows-only, and should avoid clobbering `imgui.embedded.ini` in consumer output.

**Primary recommendation:** Add an opt-in `AfterTargets="Build"` target to `MdCad.Avalonia.Control.csproj` that runs a repo-local C# console helper, uses `cmake --build build-vulkan --config Release --target mdCAD`, updates the committed `runtime\win-x64\mdCAD.exe`, and then explicitly recopies only `mdCAD.exe` into the current build output’s `mdcad-runtime\` folder.

## Architecture Patterns

### Recommended Project Structure
```text
samples/
├── avalonia-mdcad-control/
│   ├── MdCad.Avalonia.Control.csproj
│   ├── runtime/win-x64/                  # committed curated runtime bundle
│   └── tools/MdCad.WindowsRuntimeRefresh/
│       ├── MdCad.WindowsRuntimeRefresh.csproj
│       ├── Program.cs
│       └── RuntimeRefreshOrchestrator.cs
└── avalonia-mdcad-control.tests/
    └── RuntimeRefreshHelperTests.cs
```

### Pattern 1: Reuse the control project as the hook point
**What:** Put the MSBuild target in `samples/avalonia-mdcad-control/MdCad.Avalonia.Control.csproj`, because that project already owns the runtime source bundle and the transitive `mdcad-runtime\...` copy contract.  
**When to use:** For both direct control builds and host builds that reference the control via `ProjectReference`.  
**Why:** Hooking hosts duplicates logic and misses the authoritative runtime source directory.

### Pattern 2: Use CMake as the helper’s native-build API
**What:** The helper should launch:
```text
cmake --build <repo>\build-vulkan --config Release --target mdCAD
```
**When to use:** Every runtime refresh.  
**Evidence:** Local execution succeeded and produced `build-vulkan\bin\Release\mdCAD.exe`; `build-vulkan\CMakeCache.txt` confirms `USE_VULKAN:BOOL=ON` and Visual Studio generator state.

### Pattern 3: Refresh the committed source bundle, then explicitly refresh only the current build output executable
**What:** The helper should:
1. Build `mdCAD` in `build-vulkan`
2. Copy `build-vulkan\bin\Release\mdCAD.exe` to `samples\avalonia-mdcad-control\runtime\win-x64\mdCAD.exe`
3. Copy that executable to `$(TargetDir)mdcad-runtime\mdCAD.exe` for the current build

**When to use:** In the opt-in post-build target.  
**Why:** `AfterTargets="Build"` runs after the control project’s normal `CopyFilesToOutputDirectory` step, so without an explicit second copy the current control build output can stay stale.

### Pattern 4: Preserve `imgui.embedded.ini` as a seeded/runtime-state file, not a forced-refresh artifact
**What:** Do **not** force-overwrite `imgui.embedded.ini` in consumer output during the refresh target.  
**When to use:** Always, unless a later phase explicitly changes the runtime bundle contract.  
**Evidence:** The source bundle file is `1040` bytes, but an existing host output copy was `1034` bytes with a different hash after prior runs, while the csproj uses `CopyToOutputDirectory=PreserveNewest`. That is consistent with consumer-output runtime state being intentionally allowed to diverge from the committed seed.

### Anti-Patterns to Avoid
- **Do not reintroduce PowerShell** through `Exec` or script wrappers.
- **Do not add repo-root fallback logic** to the runtime resolver; Phase 48 locked output-rooted resolution.
- **Do not auto-configure `build-vulkan`** inside the helper; generator/toolchain selection is a separate concern and the phase only requires rebuild-in-existing-path behavior.
- **Do not wipe `runtime\win-x64` wholesale** before copying; that is riskier than the actual requirement.
- **Do not make the refresh target default-on** for every `dotnet build`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Native build invocation | Shell-quoted command strings / PowerShell wrappers | `ProcessStartInfo.ArgumentList` calling `cmake` directly | Avoids quoting bugs and satisfies the no-PowerShell requirement |
| Native build target discovery | VS project-path probing | `cmake --build ... --target mdCAD` | Stable across generator output layout |
| Consumer runtime propagation | New custom host copy system | Existing `Content` + `Link` + `CopyToOutputDirectory` contract in the control project | Already proven in Phase 48 |
| Runtime path selection | New configurable runtime override | Existing `MdCadRuntimeResolver.Resolve()` | Keeps `AppContext.BaseDirectory\mdcad-runtime\mdCAD.exe` contract intact |
| Full runtime directory sync | Delete-all/repopulate behavior | Targeted `mdCAD.exe` refresh plus seed-file preservation | Avoids clobbering curated/runtime-mutated assets |

**Key insight:** Phase 52.1 is not a packaging redesign; it is a controlled automation layer on top of the packaging seam Phase 48 already established.

## Common Pitfalls

### Pitfall 1: Post-build runs too late to refresh the current output
**What goes wrong:** The committed bundle updates, but `samples/avalonia-mdcad-control/bin/.../mdcad-runtime/mdCAD.exe` from the just-finished build remains stale.  
**Why it happens:** `AfterTargets="Build"` fires after normal output copy.  
**How to avoid:** After the helper updates the committed source bundle, explicitly copy `mdCAD.exe` into the current `$(TargetDir)mdcad-runtime\`.  
**Warning signs:** Source bundle hash changes, current build output hash does not.

### Pitfall 2: Clobbering `imgui.embedded.ini`
**What goes wrong:** A developer’s persisted embedded layout in consumer output gets overwritten on every build.  
**Why it happens:** Forced post-build recopy ignores the existing `PreserveNewest` seed/runtime-state behavior.  
**How to avoid:** Refresh the committed seed only when intentionally requested, and do not force-copy `.ini` into output as part of the helper target.  
**Warning signs:** `imgui.embedded.ini` in host output keeps snapping back after mdCAD runs.

### Pitfall 3: Trying to configure `build-vulkan` from the helper
**What goes wrong:** The helper becomes responsible for generator selection, SDK detection, and first-time machine setup.  
**Why it happens:** It seems convenient to “make it work end-to-end.”  
**How to avoid:** Require an already-configured `build-vulkan` directory with `CMakeCache.txt`; fail fast with actionable guidance otherwise.  
**Warning signs:** Helper starts needing generator strings, SDK install logic, or toolchain branching.

### Pitfall 4: Making refresh always-on
**What goes wrong:** Every host build rebuilds native mdCAD, slowing inner-loop work and making non-Windows or non-Vulkan environments noisy/failing.  
**Why it happens:** Post-build targets default to active.  
**How to avoid:** Gate with a property such as `MdCadRefreshWindowsRuntime=true`; keep default false.  
**Warning signs:** Plain `dotnet build` of hosts unexpectedly invokes CMake.

### Pitfall 5: Treating the committed bundle as the only thing that must update
**What goes wrong:** The repo copy is fresh, but the just-built host/control output still launches the previous executable until a second build.  
**Why it happens:** Current output already copied before refresh ran.  
**How to avoid:** Explicitly update both the committed bundle and the current build output executable in the same target.  
**Warning signs:** Hashes match between `build-vulkan` and committed runtime, but not between committed runtime and current `bin/.../mdcad-runtime`.

## Code Examples

Verified repo patterns and the recommended extension point:

### Existing packaging contract
```xml
<Content Include="runtime\win-x64\**\*">
  <Link>mdcad-runtime\%(RecursiveDir)%(Filename)%(Extension)</Link>
  <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
  <CopyToPublishDirectory>PreserveNewest</CopyToPublishDirectory>
</Content>
```
**Source:** `samples/avalonia-mdcad-control/MdCad.Avalonia.Control.csproj`

### Existing runtime resolution contract
```csharp
string runtimeRoot = Path.GetFullPath(Path.Combine(baseDirectory, "mdcad-runtime"));
string executablePath = Path.Combine(runtimeRoot, "mdCAD.exe");
```
**Source:** `samples/avalonia-mdcad-control/Host/MdCadRuntimeResolver.cs`

### Validated minimal native rebuild command
```text
cmake --build build-vulkan --config Release --target mdCAD
```
**Source basis:** Executed locally on 2026-05-18; produced `build-vulkan\bin\Release\mdCAD.exe`.

### Recommended MSBuild hook shape
```xml
<PropertyGroup>
  <MdCadRefreshWindowsRuntime Condition="'$(MdCadRefreshWindowsRuntime)' == ''">false</MdCadRefreshWindowsRuntime>
</PropertyGroup>

<Target Name="RefreshPinnedWindowsRuntime"
        AfterTargets="Build"
        Condition="'$(OS)' == 'Windows_NT'
               and '$(DesignTimeBuild)' != 'true'
               and '$(MdCadRefreshWindowsRuntime)' == 'true'">
  <Exec Command='dotnet run --project "$(MSBuildProjectDirectory)\tools\MdCad.WindowsRuntimeRefresh\MdCad.WindowsRuntimeRefresh.csproj" -- --repo-root "$(MSBuildProjectDirectory)\..\.." --build-dir "$(MSBuildProjectDirectory)\..\..\build-vulkan" --runtime-dir "$(MSBuildProjectDirectory)\runtime\win-x64" --output-runtime-dir "$(TargetDir)mdcad-runtime" --configuration Release'
        WorkingDirectory="$(MSBuildProjectDirectory)" />
</Target>
```
**Source basis:** Recommended pattern derived from the existing control csproj ownership of `runtime\win-x64` and the validated CMake build command.

## Open Questions

1. **Should the helper ever overwrite the committed `imgui.embedded.ini`?**
   - What we know: The phase requirement specifically calls out copying `mdCAD.exe`; current consumer outputs can legitimately diverge from the committed `.ini`.
   - What's unclear: Whether the team still wants the old PowerShell script’s “refresh `.ini` too” behavior.
   - Recommendation: Default to preserving the committed `.ini` unless a human explicitly refreshes that curated seed on purpose.

2. **Should the helper support first-time configure if `build-vulkan` is missing?**
   - What we know: The phase scope says “rebuild mdCAD in `build-vulkan`,” and the repo already has a configured `build-vulkan`.
   - What's unclear: Whether future maintainers will expect one-shot bootstrap behavior.
   - Recommendation: Do not add configure/bootstrap in Phase 52.1; fail with a clear message that `build-vulkan` must already exist.
